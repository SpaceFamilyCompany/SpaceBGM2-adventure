# 自己改善

作業から得た学びを、次の作業の品質・速度・安全性に生かす。自己改善とは、AIが承認なしにルールやスキルを書き換えることではない。**事実を残し、学びにまとめ、必要なときだけ提案し、所長の承認を得てから反映する。**

## 使うとき

- セッションを終えるとき。報告書（`gadget-report`）を出したあとに回す
- 所長が「自己改善を回して」「振り返って」「学びを残して」と言ったとき
- 同じ失敗・手戻り・確認漏れが、2回目に起きたとき

単発の作業で、将来に残す学びがないときは、無理に回さない。そのときは「今回は残す学びなし」と1行で返す。

## 回す前に

1. Homeの`AGENTS.md`の共通ルールを読み直す。今回の作業に関わる差分がないか確認する
2. Homeで`git status --short`を見る。所長の未コミットの変更は、消さず、巻き戻さず、上書きしない。重なるなら止めて聞く
3. 今回のセッションで扱ったリポジトリと、変えたものの一覧を作る

## ループ

`観察 → 学び → 提案 → 検証 → 承認 → 反映`。順番を飛ばさない。

### 1. 観察（事実を集める）

コマンドの結果、公開後の確認、所長が直した点を、事実として並べる。推測と事実を分ける。

- 成功にできるもの：終了コード、テスト、公開後の表示確認など、確かめた証拠があるもの
- 失敗：テスト失敗、確認できなかったタイムアウト、所長の再指示
- **証拠が足りないもの（画面を見ていない、外部に届いたか確認していない）は、成功にしない**。「未確認」と書く

### 2. 学び（`learnings/`に追記する）

再利用できる学びだけを、`learnings/YYYY-MM.md`に追記する。月ごとに1ファイル。見出しは`## YYYY-MM-DD`。

- 区分を頭に付ける：`成功`・`失敗`・`学び`・`ギャップ`（スキルや手順に足りないもの）・`テクニック`
- 再現できる条件と、次回の対策を書く。「気をつける」だけで終えない
- **追記専用**。既存の行は直さない。間違いは、訂正の行を足す
- 書かないもの：秘密の値（キー、トークン、パスワード）、会議や相談の中身、個人情報、時系列の作業ログ、AIとの会話の記録
- 作業ログと会話の記録は、リポジトリに入れない。Notionにも置かない。節目の記録は報告書に書く
- 同じ学びが、すでにあれば、重複して書かない。先に`learnings/`を検索する

### 3. 提案（`proposals/PROPOSALS.md`に書く）

共通ルール・スキル・テンプレート・運用を変える必要があるときだけ、提案を1件書く。**1提案＝1変更＝1つの対象**。

提案を出す条件は、次のどれか。

- 同じ`ギャップ`が、2回以上出た
- 手順どおりにやると、確実に失敗する箇所が見つかった
- 毎回必要な前提が、どこにも書かれていない
- スキルの`description`が原因で、発火しなかった、または誤って発火した

書式は`proposals/README.md`にある。状態は`proposed → validated → approved → promoted`、却下は`rejected`（理由を必ず残し、再提案しない）。

コードを直すだけで終わり、再利用できるルールの変更がないときは、提案を作らない。

### 4. 検証

提案を反映する前に、変更前後を同じ条件で比べる。テスト、`--check`などの検査、実機の確認を使う。**検証済みは、承認済みではない。**

### 5. 承認（所長だけ）

- 所長に、提案の内容・期待する効果・副作用・検証結果を見せる
- 所長が**チャットで「承認」と明示した提案**、または**ダッシュボード（026）の確認画面で承認した提案**だけを、`approved`にする。承認した日時と、所長の言葉の要点（ダッシュボードなら、承認した旨と操作の記録）を、提案に残す
- AIが自分で`approved`を付けない。承認を、推測や、沈黙で決めない
- ダッシュボード以外のボタンが押された、画面を開いた、などは、承認ではない。ダッシュボードでは、確認画面で「内容を読みました」にチェックして、承認ボタンを押したときだけが承認
- ダッシュボードの承認は、`proposals/PROPOSALS.md`の状態を`approved`にして記録するだけ。ルールやスキルの本体は、承認のあとに、6の手順で別に反映する。AIがダッシュボードの承認ボタンを押すことはない

### 6. 反映

承認された提案だけを反映する。

- スキルは、**正本のHome**の`.claude/skills/`を直し、`SHARED_SKILLS`の写し（`publish`）で配る。写しは直さない
- 共通ルールは、Homeの`AGENTS.md`と`CLAUDE.md`を先に直し、ほかのリポジトリへ写す。FamilyLineBotは、ブランチとプルリクエストで入れる
- 変更は、理由が追える小さなコミットにする。反映したら、提案の状態を`promoted`にして、コミットを記録する

## 所長への返事

回し終えたら、次を短く返す（1画面に収める）。

- 記録した学びの件数と、いちばん大事な1件
- 提案の件数と、承認待ちの一覧（なければ「提案なし」と、理由を1行）
- 未確認のまま残っていること

## 禁止

- 観察・学び・提案・検証を飛ばして、ルールやスキルを直接直す
- 所長の承認を、捏造する、推測する
- 証拠のない成功を、記録する、報告する
- 所長の未コミットの変更を、`reset`・強制上書き・削除する。`git reset --hard`、force push
- 秘密の値や、個人情報を、学びや提案に書く
- 安全装置に止められた操作を、別の手段で回避する。止められたら、所長に任せる
- 許可された範囲を超えて、他のプロジェクトの秘密ファイルを探す

## 書く前の点検

学びと提案を書いたら、`ja-writing`の「書く前の点検」を通す。主語と目的語を省かない。名詞だけで止めない。和文と英数字の間にスペースを入れない。
